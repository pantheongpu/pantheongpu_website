# Pantheon GPU Website

This is the **public** MkDocs Material site for Pantheon (https://pantheongpu.com),
a CUDA/ROCm GPU stress and diagnostics suite. The site serves documentation,
release downloads, and a live benchmark leaderboard.

Pantheon's source is public at `pantheongpu/pantheon`, which carries only
source, tests, and docs — it builds no releases of its own. This repository is
the release host: the Release workflow checks out a tag there, builds the wheel
and source archives, and publishes them here. From v1.1.0 a release ships a
Python wheel; v1.0.19 and earlier shipped a Debian package and Nuitka bundles.

`pantheongpu/pantheongpu` is the older private repository and is being wound
down; the Mirror Pantheon Release workflow still exists to mirror its releases.

Even though the source is public, this repo must never contain a copy of it
(`pantheon.py`, `monitor.py`, `kernels/`, ...). Two sources of truth for the
same code drift, and tests enforce the separation.

## Essential Commands
- **Install:** `python3 -m pip install -r requirements.txt`
- **Test:** `python3 -m pytest`
- **Regenerate benchmark data:** `python3 website_utils/generate_web_data.py`
- **Build check (strict):** `python3 -m mkdocs build --strict`
- **Local preview:** `mkdocs serve`

Run pytest and the strict build before every push; CI repeats both on
Python 3.11 and 3.12 and fails if generated data has drifted.

## Data Pipeline
- `database/pantheon_report_*.json` — raw benchmark reports emitted by Pantheon.
- `website_utils/generate_web_data.py` — folds reports into
  `docs/assets/web_data.json` (and `unsupported_workloads.json`), keeping the
  best score per GPU identity, test, and Pantheon version.
- After adding or changing reports in `database/`, regenerate
  `docs/assets/web_data.json` and commit it alongside the reports. Never
  hand-edit generated files.
- `docs/release.md` is generated by `website_utils/update_release_page.py`, run
  from both the Release and Mirror Pantheon Release workflows. Do not hand-edit
  it; to correct the page, fix the generator and re-run it.

## Releasing
1. Bump `VERSION` in `pantheongpu/pantheon` (via PR) and tag it `vX.Y.Z`. The
   Release workflow refuses a `v`-prefixed ref that disagrees with `VERSION`.
2. Dispatch **Release** here with `ref=vX.Y.Z` and `dry_run=true`. The dry run
   builds, installs the wheel into a clean venv with site-packages read-only,
   and renders the release page — without publishing anything.
3. Re-dispatch with `dry_run=false`. Publishing also regenerates
   `docs/release.md`, pushes it to `main`, and dispatches Publish Website —
   a `GITHUB_TOKEN` push does not trigger workflows, so that last step is
   explicit rather than incidental.
4. `docs/getting-started.md` pins the version in its install command, and a
   test asserts that exact string. Both need updating in the same PR.

## Hard Rules
- **This repo is public.** Benchmark reports must not contain host identifiers
  (`network_info`, hostname, IP address); a regression test rejects them.
  Pantheon releases up to v1.0.16 still emit `network_info`, so run
  `python3 website_utils/sanitize_reports.py` after importing new reports.
- Reports marked `partial`, `failed`, or `incomplete` are excluded from the
  leaderboard, as are multi-GPU-only workloads (`all_reduce`, `p2p_thrasher`).
- All GitHub Actions jobs run on self-hosted Linux runners (test-enforced).
- Frontend dependencies are vendored (`docs/js/apexcharts.min.js`); no CDNs.

## Conventions
- Use "We" in documentation and outreach copy (team voice).
- `tests/test_website_regressions.py` pins site behavior (script scoping,
  accessibility, nav structure); add a regression test when fixing a site bug.
